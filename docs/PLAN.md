## Где мы сейчас

Milestone 1 (пилот, $200) собран: живой каталог на всех 737 активных товарах
FashionGo, фильтры, клиентские ссылки, Chrome-расширение с импортом. Осталась
публикация на Cloudflare.

## Что уже сделано

- **Каталог** — Next.js 16 + shadcn/ui, деплой как Cloudflare Worker через
  `@opennextjs/cloudflare`. Сетка карточек, галерея фото, свотчи цветов,
  фильтр по категориям, бейдж New (товары младше 30 дней), «Copy to order».
- **Данные** — весь активный каталог аккаунта itoo (775 карточек, 737 после
  схлопывания перезалитых стилей) вытянут `app/scripts/pull-seed.mjs` и лежит в
  `app/src/data/fashiongo-seed.json` (1.6 МБ). Цена = цена FashionGo минус $1.
  У каждого товара — ряд размеров, разбивка упаковки и минимальный заказ.
- **Админ/клиент** — переключатель без авторизации (заглушка, как договорились).
  В админ-виде: чекбоксы на карточках → «Copy link» собирает ссылку с выбранными
  товарами. Клиентская ссылка открывается сразу в клиентском виде.
- **Превью в мессенджерах** — OG-теги рендерятся на сервере, ссылка
  разворачивается в карточку с фото товара.
- **Синхронизация** — расширение читает токен из `localStorage` открытой сессии
  vendoradmin, тянет товары и шлёт сырой JSON в `/api/sync`; маппинг — на
  сервере (один протестированный экземпляр кода). Полная перезапись каталога,
  без merge и разрешения конфликтов — как и договаривались для пилота.
- **Тесты** — 216 тестов (Vitest + Testing Library), включая прогон на реальных
  данных FashionGo и тесты интерфейса.

## Что осталось для сдачи M1

1. Опубликовать на Cloudflare Workers (нужен API-токен или подключение репо в
   дашборде: root `app`, build `npx opennextjs-cloudflare build`, deploy
   `npx opennextjs-cloudflare deploy`).
2. Прописать боевой домен в `extension/manifest.json` (сейчас там localhost и
   `*.workers.dev`).
3. Прогнать демо целиком: пустой каталог → Sync → товары появились → выбрать
   несколько → ссылка клиенту.

## Реверс-инжиниринг FashionGo (важное знание)

Публичного API для выгрузки каталога нет — подтверждено их поддержкой. Поэтому
работаем через API самой админки:

- `GET /api/crypto/key?default=false` → RSA-ключ.
- Пароль шифруется AES-256-CBC случайным 32-символьным hex-ключом (первые 16
  символов — IV), сам ключ шифруется RSA PKCS#1 v1.5 → `POST
  https://id.fashiongo.net/api/auth/login` → JWT (~30 дней).
  **Грабли:** экспонента приходит как `10001` — нечётная длина, `Buffer.from(hex)`
  молча режет её; нужен паддинг нулём.
- `GET /api/items?pn=1&ps=20&saleType=W&pageType=1` — список (775 активных).
  `ps` — только из их набора значений, 20 работает, 10 и 24 отклоняются.
- `GET /api/item/{id}` — карточка; **реальные цвета и галерея — в `image[]`**
  (массивы `color`/`size`/`pack` в корне — это справочники, не значения товара).
- **Размеры и упаковка.** У товара только `sizeId` и `packId` — значения ищутся в
  справочниках из той же карточки. `sizeDescription2` = ряд размеров через `;`
  («S;M;L»), `packDescription` = разбивка через `-` («2-2-2»), позиции совпадают
  один в один; сумма = минимальный заказ (`item.minTQStyle`). `packId` 0/null —
  товар продаётся россыпью, минимум задан только числом. Имена `sizeName`/
  `packName` — свободный текст, у части записей там мусор; админка сама читает
  описания, и мы тоже.
- **Даты.** В списке товаров админка показывает `_activatedOn` и от него же
  считает свой бейдж «new»; `_createdOn` («Upload Date» в их сортировке) — дата
  загрузки, у отлежавшегося черновика она на недели раньше. Каталог датирует
  товар по `_activatedOn`.
- **Один стиль может быть залит несколько раз** — 37 номеров из 775 активных
  повторяются (перезаливка). Каталог схлопывает их, оставляя свежую карточку.
- `GET /api/misc/categories` — имена категорий с количеством: `"Tops (299) "`.
  У товара `categoryId` — это подкатегория; человеческое имя даёт
  `parentCategoryId` из карточки.
- Картинки: `fg-image.fashiongo.net`, варианты `/list/` и `/large/`, отдаются
  публично без авторизации и реферера — хотлинк работает.
- Токен админки лежит в `localStorage.token`.

## Milestone 2 ($800) — бэклог

**Обязательное по контракту:**

- **База данных.** Сейчас каталог живёт в памяти изолята Worker: после
  перезапуска возвращается к seed-данным. Нужен Cloudflare D1 (schema уже
  спроектирована под `Product`), store подменяется за тем же интерфейсом
  `CatalogStore`.
- **Еженедельная синхронизация** с экраном review/publish: что добавилось, что
  подорожало, где не нашлось фото — и только потом «Publish».
- **Фото на Cloudflare R2.** Сейчас хотлинк на их CDN — для пилота нормально, но
  ссылки не под нашим контролем и могут протухнуть. Перекладывать при импорте.
- **Дубликаты и неполные данные** — алерты, как обещано в оффере.
- **Скрытие товаров вручную** (sold out) — флаг в БД, не трогая FashionGo.
- **Документация и видео-прохождение** для нетехнической команды.

**Идеи Алексея (обсудить с клиентом, скорее всего в M2/M3):**

- **API-first фоновая синхронизация.** Расширение работает в фоне: держит токен
  из сессии админки, периодически обновляет его, при 401 просит перелогиниться.
  Новые товары встают в очередь, картинки подтягиваются постепенно; в интерфейсе
  подсвечивается «требуется синхронизация». Это снимает ручной шаг совсем.
- Отдельный шаг «дотянуть картинки» — метаданные приходят сразу, фото догружаются
  фоном.

**Дальше отдельными этапами (M3+):** интеграция с их чат-платформой (у неё есть
API, ссылки на категории стабильные), заказы, учёт остатков.

## Договорённости по продукту (с созвона 03.08.2026)

- FashionGo — единственный источник правды, каталог зеркалит 1:1.
- Цена каталога = цена FashionGo − $1.
- Фильтр по категориям + возможность собрать выборку из разных категорий.
- Любой товар можно скрыть вручную (распродан).
- Клиент получает короткую ссылку: конкретные товары или категория целиком.
- «New arrivals» — автоматически, товары младше 30 дней по дате публикации в
  FashionGo (`_activatedOn`, её же показывает их админка). Сейчас таких 38 из 737.

клиентские тексты — на английском, этот файл удалить перед передачей.
